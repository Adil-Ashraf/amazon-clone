## High Priority Issues

**1. Checking out the same cart twice at once creates two orders and decrements stock twice**
- **Where:** [checkout_service.rb:12-21](app/services/orders/checkout_service.rb#L12-L21)
- **Problem:** The empty-cart check (line 13) and the cart-item load (line 20) both run before any lock is taken. Only product rows are locked. Two overlapping requests for the same cart (two tabs, or a retried submit) both read the items. The second waits on the product lock, then re-validates stock successfully and creates a duplicate order.
- **Evidence:** One cart holding one unit, two threads 50 ms apart produced `orders created: 2, stock 5 -> 3`. I added 200 ms of latency inside the transaction to make the overlap deterministic. Without it, the window is the transaction's own duration: 43 queries, so tens of milliseconds.
- **Mitigation that already exists:** `turbo_submits_with` disables the button, which stops double-clicks but not two tabs or replayed requests.
- **Also:** [README.md:137-139](README.md#L137-L139) claims concurrency-safe checkout. That's true across different carts, but not for the same cart.
- **Fix:** Call `cart.lock!` as the first statement inside the transaction, and move the empty-cart check after it. Add a threaded spec for this case.

**2. N+1 on `categories` for cart, checkout, order history and the add-to-cart stream (measured)**
- **Why:** `product_image_tag` always builds the fallback tile, and the tile reads `product.category` ([products_helper.rb:95](app/helpers/products_helper.rb#L95), [:133](app/helpers/products_helper.rb#L133)). The affected queries preload only `:product`.

| Page | Query | Measured |
|---|---|---|
| `/cart` | [carts_controller.rb:7](app/controllers/carts_controller.rb#L7) | 8 extra `SELECT categories … LIMIT 1` for 8 items |
| `/checkout/new` | [checkouts_controller.rb:8](app/controllers/checkouts_controller.rb#L8) and `:41` | 8 extra |
| `/orders` | [orders_controller.rb:6](app/controllers/orders_controller.rb#L6) | 5 extra (one per distinct category) |
| `POST /cart_items` stream | [cart_items_controller.rb:88](app/controllers/cart_items_controller.rb#L88) | 8 extra |

- **Fix:** Change these to `includes(product: :category)`. Orders show and wishlist already do this correctly.

**3. A signed-in user without a cart gets 500s**
- **Evidence:** `GET /cart` and `POST /cart_items` raise `Pundit::NotDefinedError (NilClassPolicy)`; `GET /checkout/new` raises `NoMethodError: cart_items for nil`.
- **Why it can happen:** Registration saves the user and creates the cart as two separate writes outside a transaction ([registrations_controller.rb:10-11](app/controllers/registrations_controller.rb#L10-L11)). Any user created by seeds or the console has no cart. 12 of the 13 users in dev have no cart; they can't sign in only because their passwords are random.
- **Fix:** Use `current_user.cart || current_user.create_cart!` in one place, or create the cart lazily.

**4. A quantity of 0, a negative number or text in `POST /cart_items` raises an unhandled `RecordInvalid`**
- **Where:** [cart_items_controller.rb:7](app/controllers/cart_items_controller.rb#L7) and [cart_service.rb:16-26](app/services/carts/cart_service.rb#L16-L26)
- **Evidence:** `quantity=0` returns 422 with the Rails exception page. A Turbo Stream request fails silently for the user.
- **Also:** A negative quantity on an existing line silently reduces it, because `add_item` computes `current + (-3)`.
- **Fix:** Reject quantities below 1 in the service, raising a domain error that the controller already knows how to render.

## The four fixes

**1. Same-cart checkout race**
- Inside the transaction, checkout now locks the cart first. Only after that does it read the cart items and check the cart isn't empty.
- The rest is unchanged: products are locked in `product_id` order, stock is re-checked under the lock, then the order is created, stock decremented and the cart cleared, all in one commit.
- A second checkout of the same cart now waits for the first to finish, then finds the cart empty and gets `EmptyCartError`, which the controller already handles by redirecting to the cart.
- **One small extra change:** clearing the cart now deletes only the lines that were actually ordered. Before, a line added from another tab during checkout would have been deleted without being bought. The query count is the same as before.

**2. Category N+1**
- The cart, checkout and cart-items queries now use `includes(product: :category)`, and order history uses `includes(order_items: { product: :category })`.
- I changed only those queries. Order detail and the wishlist were already correct.

**3. Users without carts**
- New `User#ensure_cart!` returns the existing cart or creates one with `create_or_find_by!`. That relies on the existing unique index on `carts.user_id`, so two simultaneous first requests end up sharing one cart instead of creating two.
- It's used by the cart page, the add/update/remove cart actions, checkout, and `CheckoutService`.

**4. Invalid quantities**
- `CartService#add_item` now rejects anything that isn't a whole number of at least 1 with a new `InvalidQuantityError`. A negative "add" can no longer shrink an existing line.
- `update_quantity` still treats 0 as "remove", because the cart's minus button relies on that. Negative numbers and non-numbers are now rejected.
- The controller parses strictly, so `"abc"` or `"1.5"` is rejected instead of turning into 0 and removing the line.
- The errors show up in the existing error toast (Turbo) or the flash message (plain HTML).
